# Ручная публикация Velora

## Перед сборкой новой версии

1. Убедитесь, что номер в `gradle.properties` **увеличен** относительно последнего GitHub Release: `APP_VERSION_CODE` и `APP_VERSION_NAME`. Сборка с тем же номером не является обновлением для установленного приложения.
2. Добавьте `release/notes-v<version>.md` с коротким разделом `## Что нового` и честными ограничениями. Документ `docs/VELORA_STATUS.md` фиксирует результаты испытаний.
3. Закоммитьте **версию, заметки и исходный код до запуска** Android CI. Подписанный APK должен содержать правильный `versionCode` и соответствовать исходному коммиту. После успешной сборки избегайте изменений в `main`: workflow публикации отклоняет неразрешённые изменения между исходным коммитом APK и публикацией.
4. GitHub → Actions → [Android release APK](https://github.com/AlekseyVinokurov/Velora/actions/workflows/android-release.yml) → **Run workflow** → ветка `main`, `arm64` для приёмки Pixel 8 или `universal` для широкого распространения. Тот же закреплённый release-ключ; не меняйте `applicationId`.
5. После успешной сборки проверьте `stable-build.json` (версию, подпись и исходный коммит), установите APK поверх предыдущей версии и выполните функциональную приёмку. **Artifact не публикует обновление** для пользователей.
6. **Только после разрешения владельца** переходите к workflow публикации ниже. Он продвигает **ровно тот же** проверенный APK в GitHub Releases без повторной сборки или смены ключа.

**Правило кандидатов:** если после установки тестового Artifact потребовалось исправить код и пересобрать APK, увеличьте `versionCode` ещё раз (например, `100005 → 100006`) **до новой сборки**. Иначе устройство, на котором установлен предыдущий кандидат, и встроенный updater не смогут различить два APK с одинаковым номером. После приёмки продвигайте в Releases **байт-в-байт тот же** проверенный Artifact; тогда дополнительных сборок и конфликтов номеров не будет.

Для версии, предназначенной не только для Pixel 8, выбирайте `universal` и тестируйте на Pixel 8 **именно этот APK**. Не надо выпускать отдельно arm64-кандидат и затем другой universal-APK с тем же `versionCode`.

## Публикация проверенного APK

1. Откройте GitHub → **AlekseyVinokurov/Velora → Actions**.
2. Выберите **Publish Velora Release**.
3. Нажмите **Run workflow**, оставив ветку `main`.
4. Введите `run_id` успешной Android release-сборки. Это число в конце ссылки на её запуск: `…/actions/runs/123456`.
5. Запустите публикацию. Версия, APK и остальные данные определятся автоматически.
6. После успешного завершения откройте **Summary** запуска: там будут ссылки **Release** и **APK**. Прямой APK также появится в разделе **Releases** репозитория.

Публикуйте до следующих изменений приложения в `main`, пока артефакт сборки не истёк. Пересборка, PAT и дополнительные секреты не нужны. Самостоятельная успешная Android-сборка ничего не публикует.

Существующие релизы и теги не заменяются. Полностью загруженный draft от той же сборки и того же коммита публикации можно безопасно продолжить повторным запуском с тем же `run_id`; неизвестный, неполный или изменённый draft остановит публикацию. Не удаляйте и не заменяйте его файлы для обхода проверки.

Если GitHub вернул ошибку, журнал покажет HTTP-код, метод и endpoint без токена. Исправьте указанную причину перед новым ручным запуском.

Для сопровождающих: подпись и Android identity проверяет исходный CI. Публикация проверяет происхождение и успешность этих проверок, digest архива из GitHub API, квитанцию, постоянный certificate pin и SHA-256 фактических байтов APK. Между исходным коммитом APK и коммитом публикации допускаются только файлы механизма публикации, его тестов, этой инструкции и release notes. В metadata сохраняется исходный `sourceCommit`; тег указывает на проверенный коммит публикации. Готовый APK скачивается только на GitHub-hosted runner.
