# Velora Bypass: реализация и пределы проверки

## Управление

Доступен вручную из настроек Velora и списка прокси. Настройки порта, секрета,
пула, буферов, CF/FakeTLS и DC сохраняются. Разрешение запуска — токен только
текущего процесса, передаваемый сервису из обработчика нажатия. Сохранённые
`enabled/manual_enabled/auto_start` сами по себе ничего не запускают; при старте
процесса они сбрасываются. BootReceiver отключён и инертен, автодетектор инертен,
музыкальные запросы не запускают сервис. Нет sticky restart, WorkManager, alarm,
heartbeat, постоянного wake lock или автоматического восстановления после VPN.

Сервис specialUse работает с уведомлением «Velora Bypass» и кнопкой остановки.
Он применяет маршрут через `ConnectionsManager.setProxySettings` только после
успешного native StartProxy и проверки локального порта. `mainconfig`,
`SharedConfig.currentProxy` и список прокси не записываются. Остановка восстанавливает
актуальные сохранённые Telegram ProxySettings, включая WEB-прокси. Изменение
сохранённых proxy settings пользователем останавливает Bypass. VPN не меняется:
при обнаружении VPN запуск отклоняется / текущий сервис останавливается.

## Сеть и native-код

Java → JNI (`jni_bridge.c`, совместимые soundgram symbols) → Go c-shared
`libtgwsproxy.so`, исходник `soundgram/wsproxy/tg-ws-proxy.go`.
Движок сохранён; прежние непрозрачные `.so` больше не упаковываются. Workflow
собирает исходник для двух ARM ABI через Go/закреплённый Android NDK на GitHub-hosted
runner в игнорируемый `.local-build/native-libs`, добавляя неизменённый libpine.
Gradle требует пересобранную библиотеку; исходники и tracked binaries не меняются
во время сборки. Ключ и сертификат приложения прежние.

Слушатель — только `127.0.0.1`, порт по умолчанию 1443. Для Telegram принимает
MTProto obfuscated transport (dd / опциональный ee FakeTLS), соединяется через
WebSocket binary over TLS с `kws{dc}.web.telegram.org` и `kws{dc}-1.web.telegram.org`
на 443; есть TCP/fallback и CF-маршруты. Для HTTP музыкальных источников тот же
listener поддерживает SOCKS5/HTTP relay; HTTPS сохраняет штатную проверку TLS.
FakeTLS — маскировка локального MTProto handshake, а не отключение проверки
сертификата внешнего WS. Внешний WS теперь проверяет цепочку и hostname.

Встроенные DC: `149.154.175.50`, `149.154.167.51`, `149.154.175.100`,
`149.154.167.91`, `149.154.171.5`; доступны пользовательские overrides.
Встроенные CF-домены (декодированы по функции из исходника):
`pclead.co.uk`, `offshor.co.uk`, `cakeisalie.co.uk`, `noskomnadzor.co.uk`, `lovetrue.co.uk`.
Дополнительно используется HTTPS-список `raw.githubusercontent.com/Flowseal/tg-ws-proxy/main/.github/cfproxy-domains.txt`,
кэш с интервалом свежести 6 часов и до трёх попыток обновления за запуск.
Это сторонняя инфраструктура; её доступность и доверенность не подтверждены.
DNS: системный resolver, UDP `1.1.1.1`, `8.8.8.8`, `77.88.8.8`, `1.0.0.1`,
`8.8.4.4`, `9.9.9.9`; DoH Cloudflare, Google, Quad9, AdGuard, OpenDNS, doh.sb.
Домен/IP/время соединения видны выбранной инфраструктуре; это не средство анонимности.

## Ресурсы — сведения из кода, не замеры

При выключенном Bypass отсутствуют его сетевые пробы, native listener, monitor,
network callback, pool refill, alarms и foreground service. После остановки
отменяются контексты, закрываются клиентские/исходящие соединения, пул и idle HTTP
connections; Go StopProxy ожидает завершения предыдущего runProxy. Загруженный Go
runtime может остаться в RAM до смерти процесса — выгрузка `.so` не обещается.

При включении: один Java executor, health thread с локальной TCP-пробой раз в
10 секунд, network callback; Go goroutines для клиентов, DNS, WS и пула.
По умолчанию пул 4 на используемый слот DC/media, настройка ограничена 2–16;
socket buffers по 256 KiB (ограничение настройки 16–1024 KiB). Это настройки,
а не оценка полного RAM. Движок использует дополнительные frame buffers, TLS cache
и кэши DNS. Пригодность WS для повторного использования проверяется по возрасту 180 секунд;
это не гарантия немедленного удаления idle entry. Bridge ping — 15 секунд.
Refill замедлен с 2 до 15 секунд; CF fallback ограничен 3 кандидатами / 4 общими
попытками, 429 backoff 15–120 секунд. Ошибка сервиса не вызывает автоматического
перезапуска; две неудачные локальные health-пробы останавливают его. При Wi-Fi/LTE
включённый движок сбрасывает пул/cooldowns, выключенный не запускается.

Пул, DNS fan-out, TLS и keepalive повышают RAM/CPU/трафик/расход батареи во включённом
состоянии. Цифры MiB, CPU%, mAh и прирост трафика без измерений не установлены.
Локальная TCP-проба подтверждает listener, а не доставку сообщения; UI отдельно
показывает состояние соединения Telegram. Нужны реальные тесты блокировок,
CF/TLS, смены сети, остановки во время загрузки и фонового воспроизведения на Pixel 8.

Проверки исходника Go в [итоговом CI #42773454999](https://github.com/AlekseyVinokurov/Velora/actions/runs/42773454999)
прошли: доверенный TLS, отказ при неверном hostname/недоверенном сертификате,
отмена listener и half-open client, три последовательных native start/stop.
Android-компиляция и подпись APK прошли; соединение с Telegram/CF на устройстве
и показатели потребления остаются непроверенными.
