# Выпуск Velora (актуальный порядок)

Все Android-сборки, Gradle, NDK/SDK, подпись и создание APK выполняются
**только на GitHub-hosted runners через GitHub Actions**. Ноутбук используется
для кода, Git и лёгких проверок. Не запускать локальные Android-сборки,
Docker или self-hosted runner. Ниже описана действующая процедура;
устаревшие локальные сценарии сборки и создания нового ключа неприменимы.

Использовать **только существующий постоянный release-ключ**, закреплённый
отпечаток из `release/certificate.sha256` и
`applicationId=io.github.alekseyvinokurov.velora`.
Новый ключ, новая подпись, другой идентификатор, переподписание уже
проверенного APK и удаление приложения для обновления запрещены.

## 1. Зафиксировать номер новой версии

В `gradle.properties` установить одновременно:
- `APP_VERSION_NAME` — следующая опубликованная версия, например `0.1.5`.
- `APP_VERSION_CODE` — целое **выше всех ранее опубликованных**, например `100005`.

Истинная текущая версия определяется последним публичным
[GitHub Release](https://github.com/AlekseyVinokurov/Velora/releases),
а не названием ветки или уже собранным Artifact.
Версию увеличивать **до** подписанной сборки; после сборки переименованием
APK или GitHub Release обновить `versionCode` невозможно.

## 2. Документация перед сборкой

- `release/notes-v<version>.md`: короткий раздел `## Что нового`
  с 1–4 пунктами, затем, при необходимости, «Важно» об ограничениях.
  Это описание использует GitHub Release и встроенное окно обновления.
- `docs/VELORA_STATUS.md`: фактическая приёмка на устройстве, известные
  ограничения, версия и статус публикации.
- README.ru.md / README.md: общая информация о проекте и ссылка на Releases;
  переписывать README при каждом выпуске не требуется.

Исходники, версия, документация и notes должны быть закоммичены до запуска
Android CI. Не делать посторонних изменений в `main` между сборкой и
публикацией — promotion workflow проверяет список изменённых файлов.

## 3. Получить подписанный APK как Artifact

Запустить вручную [Android release APK](https://github.com/AlekseyVinokurov/Velora/actions/workflows/android-release.yml)
из `main`. Для Pixel 8 допускается `arm64`; для общего релиза разумно
готовить `universal` (поддержка ABI зависит от результата CI).
Workflow проверяет приложение, подпись, версию и выдаёт
`Velora-<version>-<code>.apk` вместе с `stable-build.json`
в Artifacts (срок хранения 7 дней).

**Artifact — ещё не Release**. Встроенный updater его не видит.
Установить APK поверх предыдущего без удаления приложения;
проверить сохранение сессии, настройки, Telegram и затронутые функции.
Проверить versionName/versionCode и стабильную подпись в receipt.
Успешная сборка сама по себе не означает успешный тест на телефоне.

## 4. Выпустить тот же APK без пересборки

**Только после разрешения владельца** запустить
[Publish Velora Release](https://github.com/AlekseyVinokurov/Velora/actions/workflows/publish-existing-release.yml)
из `main` с `run_id` успешной сборки из шага 3.

Workflow проверяет происхождение Artifact, SHA-256 байтов APK,
прикреплённый сертификат, `applicationId`, версию, metadata,
подготавливает tag `v<version>`, стабильный GitHub Release,
`velora-release.json` и пользовательские release notes.
Не создаёт другой APK и не переподписывает существующий.
Публикация не заменяет существующие теги или релизы.

Точное описание: [PUBLISHING.ru.md](PUBLISHING.ru.md).
Описание защищённой облачной сборки: [GITHUB_ACTIONS.md](GITHUB_ACTIONS.md).
Протокол обновлений: [UPDATES.md](UPDATES.md).

## 5. Проверить обновление

На предыдущей опубликованной версии открыть встроенную проверку обновлений.
Она должна увидеть `releases/latest`, предложить новую версию при
`remote.versionCode > installed.versionCode`, проверить метаданные,
SHA-256, сертификат и подпись и передать APK штатному установщику Android.
Установка требует подтверждения пользователя. Проверить, что прежние
данные и авторизация сохранились. Если обновление не обнаруживается,
не удалять приложение и не подменять подписанта — проверить публичный
Release и его `velora-release.json`.

Успех host-тестов / CI, наличие Artifact, доступность Release и реальное
обновление в приложении — четыре отдельные стадии, не подменяющие друг друга.
