# Выпуск Velora

Для облачной сборки с существующим постоянным ключом используйте [GITHUB_ACTIONS.md](GITHUB_ACTIONS.md).
Эта процедура заменяет прежний запрет CI-подписи ниже. Новый ключ создавать нельзя.

Процесс проверяет и подготавливает артефакты локально. Он не выполняет push, не создает удаленный тег или GitHub Release и не загружает ключ в CI. Фактическое состояние — в [VELORA_STATUS.md](VELORA_STATUS.md).

## 1. Создать единственную постоянную подпись

Во время подготовки настоящий ключ и его отпечаток не предоставлялись. В своем интерактивном терминале запустите:

```bash
scripts/create-release-key.sh
```

Создается RSA-4096 / SHA256withRSA в PKCS#12, alias `velora-release`, срок сертификата 12 000 дней — более 30 лет. Путь по умолчанию: `$HOME/.config/velora/signing/velora-release.p12`, вне Git. Другой путь тоже должен находиться вне любого checkout. Существующий ключ или постоянный отпечаток не перезаписывается. Новый файл доступен только владельцу.

`keytool` интерактивно запрашивает уникальную длинную парольную фразу и ваши собственные поля сертификата. Пароль, организация, адрес и контакты не придумываются. Пользуйтесь менеджером паролей и не записывайте сеанс терминала. Пароли не попадают в аргументы команд или историю shell. Helper временно экспортирует только **публичный** сертификат, считает настоящий SHA-256, удаляет экспорт и записывает публичный отпечаток в `release/certificate.sha256` и [SIGNING_CERTIFICATE.md](SIGNING_CERTIFICATE.md).

Проверьте и закоммитьте эти два публичных файла. Сам keystore никогда не должен попадать в Git, APK, staging релиза или CI-артефакты. Не загружайте постоянный ключ в GitHub Actions. Если создание прервалось после генерации файла, не делайте новый ключ: зарегистрируйте существующий:

```bash
scripts/register-release-certificate.sh /абсолютный/внешний/путь/velora-release.p12 velora-release
```

Регистрация отклоняет сертификат, отличный от уже закрепленного. Перед стабильной сборкой Gradle дополнительно проверяет приватный alias, RSA-размер, срок действия и отпечаток. Исходный срок сертификата должен быть не менее 30 лет. Обычные обновления не меняют ключ или pin.

## 2. Резервные копии до распространения APK

Сделайте две зашифрованные копии **того же** keystore на разных носителях/в разных местах, вне репозиториев и артефактов сборки. Пароль храните отдельно в менеджере паролей вместе с alias и форматом. Сохраните публичный отпечаток.

Проверьте восстановление в отдельный внешний каталог: интерактивно откройте восстановленный keystore, экспортируйте публичный сертификат и сравните его SHA-256 с pin в Git. При проверке восстановления не перезаписывайте оригинал. Потеря приватного ключа/пароля не позволяет выпускать совместимые direct-APK обновления; новый ключ это не исправляет. Не предлагайте пользователям удалять STABLE для обхода ошибки подписи.

## 3. Зафиксировать исходники и версию

Подготовьте окружение и свои Telegram-параметры по [BUILDING.ru.md](BUILDING.ru.md). Явно измените `gradle.properties`:

- `APP_VERSION_NAME`: семантическая версия — запланированная `0.1.0`, затем `0.1.1` и далее.
- `APP_VERSION_CODE`: целое, сейчас запланировано `100000`, затем `100001` и далее; больше кода любого ранее опубликованного APK.

Локальный запуск Gradle не меняет версию, ABI-число к коду APK не добавляется. Опубликованная версия/тег обозначает один неизменный набор артефактов. Не переиспользуйте код версии, не перемещайте тег и не заменяйте APK пересборкой. Закоммитьте проверенные исходники, оставив дерево чистым. Сохраняйте SHA субмодулей и соответствующие native prebuilds.

## 4. Собрать и проверить настоящий STABLE APK

```bash
scripts/build-stable.sh
```

Используйте собственный внешний ключ. Wrapper запрашивает пароли без отображения, передает их только в окружение краткоживущего Gradle и отключает configuration cache. Ключ остается снаружи. Выполняется:

```bash
./gradlew --no-daemon --no-configuration-cache :TMessagesProj_AppStandalone:assembleAfatStandalone
```

Прямая команда полезна, только если ваши параметры подписи уже заданы локально. Не передавайте пароли в ее аргументах. STABLE отклоняется без `RELEASE_STORE_FILE`, `RELEASE_STORE_PASSWORD`, `RELEASE_KEY_ALIAS`, `RELEASE_KEY_PASSWORD` и совпадающего публичного отпечатка.

Wrapper проверяет `app.apk` через `aapt2`/`apksigner`: стабильный пакет, точную фиксированную версию, minSdk, APK-подпись, размер RSA и единственного закрепленного подписанта. Считается SHA-256, отклоняются встроенные keystore и приватная конфигурация. Receipt `.local-build/stable-build.json` содержит параметры реального APK и чистый source commit. Изменение исходников во время сборки отклоняется.

Тесты инструментов используют только временные случайные fixture-ключи. Их успех не подтверждает сборку настоящего APK Velora или обновление на устройстве.

## 5. Локально подготовить артефакты

Напишите достоверные release notes: итоговые изменения, известные ограничения и реальные проверки. После коммита исходников и заметок:

```bash
python3 scripts/release.py prepare \
  TMessagesProj_AppStandalone/build/outputs/apk/afat/standalone/app.apk \
  --notes /путь/к/проверенным-release-notes.md
```

Скрипт требует соответствующий receipt и чистый source commit, повторно проверяет APK и публичные метаданные последнего стабильного GitHub-релиза. Он отклоняет нерастущие версии, другой опубликованный сертификат, неправильные метаданные, сетевую ошибку и rate limit. HTTP 404 означает отсутствие публичного стабильного релиза для сравнения. Если прежний релиз не имеет метаданных, сначала вручную установите правильную нижнюю границу версии; скрипт ее не угадывает.

Новый `.local-build/releases/v<versionName>/` содержит только:

- `Velora-<versionName>-<versionCode>.apk` — проверенные байты, скопированные без пересборки.
- `velora-release.json` — данные реального APK, публичного сертификата и source commit.
- `SHA256SUMS` — хеши APK, метаданных, заметок и списка исходников.
- `SOURCE.json` — точный source commit и SHA субмодулей.
- `RELEASE_NOTES.md` — ваши проверенные заметки.

Существующий staging-каталог не перезаписывается. Keystore, пароли, Telegram-конфигурация и произвольный build-каталог не копируются.

## 6. Опубликовать вручную после разрешения

В этой задаче публикация не выполнялась. После собственного просмотра/разрешения:

1. Обеспечьте доступ к точному source commit, исходникам компонентов и notices. Для распространяемой сборки должен быть доступен соответствующий GPL-код. `SOURCE.json` — указатель, а не замена исходникам.
2. В [GitHub Releases](https://github.com/AlekseyVinokurov/Velora/releases) подготовьте **draft** на точный commit, с тегом `v<versionName>` и проверенными заметками в описании.
3. Загрузите все пять подготовленных публичных файлов. Имя `velora-release.json` и имя APK должны остаться неизменными. Проверьте хеши загруженных файлов.
4. Еще раз проверьте содержимое, затем опубликуйте стабильный релиз: **не draft и не prerelease**, пометьте latest. После публикации не меняйте артефакты.
5. Проверьте публичный API и updater с предыдущей стабильной версии. При rate limit повторите позже; ошибка API не означает успешную проверку.

Автопубликация не добавлена. Подпись/публикация в CI в будущем требуют отдельной настройки защищенных секретов и явного разрешения; в текущий процесс они не включаются автоматически.

## 7. Проверить две последовательные сборки на устройстве

**Пока не выполнено.** После получения настоящих Telegram-параметров, постоянного ключа и устройства соберите A, затем B из отдельных коммитов с растущими версиями, тем же ключом и applicationId. Нужны реальные APK приложения, не host-fixtures.

На заявленном основном устройстве Google Pixel 8 / Android 17:

1. Установите A, используйте подходящий тестовый аккаунт, приватно зафиксируйте выбранные настройки и локальные тестовые данные.
2. Проверьте пакет, сертификат и растущий versionCode обоих APK через `scripts/release.py verify` на соответствующих source commits.
3. Установите B поверх A штатным обновлением Android. Для отдельной USB/ADB-проверки сохранения данных допустимо `adb install -r /путь/к/B.apk`. Не используйте `-d`, удаление приложения или `pm clear`.
4. Убедитесь, что сохранены аккаунт/сессия, настройки и локальные файлы. Запишите обе версии, fingerprint, устройство и результат без персональных данных.
5. Отдельно проверьте опубликованный in-app путь: отсутствие релиза, офлайн/rate limit, прогресс, отмену, повтор/возобновление, разрешение источника, отказ от чужого/поврежденного APK и подтверждение Android. До реального прохождения теста нельзя заявлять end-to-end обновление через GitHub.

Публикация — отдельный ручной шаг. Не публикуйте тестовый релиз только ради формального завершения проверки. Проверки на остальных устройствах остаются открытыми.
