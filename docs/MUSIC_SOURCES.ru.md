# Музыкальные источники Velora

Срез кода `main` от 16 ноября 2026 года; навигатор — [PROJECT_MAP.ru.md](PROJECT_MAP.ru.md).
Исследованы точки поиска, разрешения аудио, рекомендаций и непосредственной передачи
плееру. Сетевые запросы и проверка на устройстве не выполнялись. «Да» ниже означает
найденную реализацию, а не подтверждённую доступность сервиса или воспроизведение.
Плеер, очередь, фоновый сервис и код приложения не менялись.

Основные разделы описывают исходный срез до M1; актуальные дополнения M1/M2 — в конце.

## Текущий механизм и выбор источника

Все пути далее относительны `TMessagesProj/src/main/java/`, кроме явных ссылок на docs.

```text
ChannelMusicFragment → MusicWebSearcher.search(query, page)
                         ├─ Hitmos HTML → WebTrack с URL → основа списка треков
                         └─ Deezer JSON → обложки / исполнители / альбомы
Выбор трека → при пустом URL: resolveHitmosSync(title, artist)
            → createWebMessageObject → playContext → MediaController
Каталог альбома/исполнителя Deezer → поиск соответствующего MP3 в Hitmos ─┘

SmartRadioEngine → SeedSelector → InnerTube search / next / browse
                                     └─ при сбое: Piped relay
                 → WaveQueueManager: фильтрация / история / кандидаты
                 → searchTrackStrict → resolveHitmosSync при неудаче
                 → createWebMessageObject → callback → очередь MediaController

Скачивание отдельно: URL → downloadTrackToExactFileSync → локальный файл
Telegram-документ отдельно: FileLoader.loadFile → файл Telegram
```

**Общий поиск.** `soundgram/music/MusicWebSearcher.java`, метод `search`, запускает
запросы Hitmos и Deezer параллельно, ожидает задачи до 4,5 секунды. В итоговый список
треков добавляются только Hitmos-результаты с непустым `downloadUrl`, затем сортируются.
Deezer обогащает обложки совпавших треков и даёт отдельные результаты исполнителей/альбомов.
Временный `deezerTracks` получает поле `preview`, но эти записи не добавляются в список
треков. `searchDeezerTracksSync` вообще возвращает пустой URL. Каталожные экраны могут
создавать записи без аудиоссылки, разрешаемые позднее. Метаданные не равны аудио.

**Выбор задан кодом**, а не общим переключателем провайдера. В исследованных точках
нет единого реестра источников или пользовательского выбора «получать аудио из X».
`searchTracksSync`, `searchTrackStrict`, `resolveHitmosSync`, методы профилей/альбомов
имеют собственные запросы и fallback. При клике `ChannelMusicFragment` повторно ищет
Hitmos, если URL пуст; если ссылка есть, передаёт её дальше. Это не замена источника
после ошибки воспроизведения непустого, но неработающего URL.

**Волна.** `soundgram/music/SmartRadioEngine.java` координирует сессию;
`soundgram/music/wave/SeedSelector.java` выбирает seeds и находит video ID.
`InnerTubeClient.java` возвращает каталожные `RawTrack`; исследованные парсеры используют
конструктор без `downloadUrl`. `WaveQueueManager.java::resolveSingleCandidate` допускает
готовый URL, но иначе вызывает `MusicWebSearcher.searchTrackStrict`, затем
`resolveHitmosSync`; без ссылки кандидат отбрасывается. Извлечение YouTube-аудио здесь
не реализовано. Поэтому резерв рекомендаций Piped не снимает зависимость Волны от Hitmos.
При динамическом пополнении найдены также жанровые плейлисты Deezer, похожие исполнители
и встроенные canonical seeds; комментарий «исключительно YouTube» не описывает всю логику.

**Граница с плеером.** В `soundgram/music/ChannelMusicFragment.java` метод
`createWebMessageObject` создаёт `TL_message`/аудиодокумент, оборачивает в `MessageObject`,
записывает `SG_STREAM|||…` с метаданными/URL и выставляет `attachPath`.
Сначала выбирается уже существующий локальный файл по имени или прежним ID/hash;
иначе остаётся URL. `playContext` передаёт список в `MediaController.setPlaylist`
и запускает `playMessage`. В `org/telegram/messenger/MediaController.java` HTTP(S)
`attachPath` распознаётся как потоковый источник. Это существующий контракт расширения;
новый провайдер не должен заставлять менять очередь или фоновый сервис.

**Скачивание не является поиском.** `MusicWebSearcher.downloadTrackToExactFileSync`
получает готовый URL и файл назначения: пробует загрузку, разрешение редиректа и повторы.
Проверяются HTTP-ответ, некоторые типы содержимого, минимальный размер и признаки
неаудиофайла. Успех этих проверок не гарантирует правильную версию композиции/полноту.
В загрузке альбома `ChannelMusicFragment` берёт URL из `SG_STREAM`, а для Telegram-аудио
вызывает `FileLoader.loadFile`. Автоматического поиска другого поставщика при сбое нет.

## Сеть, ограничения и неизвестное

- `soundgram/music/MusicNetworkHelper.java::openConnection` явно передаёт Java Proxy.
  Для `isBypassOrMirrorHost` (включая Hitmos, Deezer, Piped и подстроку `cdn`) выбран
  `Proxy.NO_PROXY`. Для остальных хостов `getActiveProxy` предпочитает запущенный локальный
  WS-сервис, затем настроенный Telegram SOCKS без `secret`, иначе прямое соединение.
  Наличие Telegram MTProxy с secret не делает его HTTP/SOCKS-маршрутом для музыки.
- Глобальный `ProxySelector` отличается: для перечисленных mirror-хостов он допускает
  настроенный SOCKS без secret. Явный `openConnection` эту ветку не использует.
  `Authenticator` также глобальный и берёт учётные данные из Telegram-настроек прокси.
  Нельзя обещать одинаковый маршрут поиска, загрузки и фактического аудиопотока,
  опираясь только на наличие настроенного прокси; полный сетевой стек плеера не исследован.
- `NO_PROXY` означает отказ от Java-прокси, а не обход Android VPN. В исследованных методах
  нет управления VPN или привязки сокетов к сети вне VPN. Действие системного VPN,
  split tunneling и DNS нужно проверять на устройстве; обязательного VPN в коде нет,
  но доступность без VPN из конкретной сети не установлена.
- В `fetchHtml` при timeout/socket/DNS есть повторы, SSL-ошибка пробрасывается.
  Методы `fetchHtmlDirect`, `fetchHtmlViaSystemProxy`, `downloadTrackDirect` и
  `resolveRedirectDirect` всё равно вызывают `MusicNetworkHelper.openConnection`.
  Их имена/комментарии не доказывают смену маршрута. Проверка TLS не отключается.
- Зеркало `rus.hitmos.fm` часто пробуется только при пустом/коротком HTML основного хоста
  (<500 символов). Исключение запроса может сразу уйти во внешний catch; длинная страница
  блокировки не обязана вызвать резерв. `resolveHitmosSync` также меняет исполнителя,
  транслитерирует запрос и ищет только название — совпадение может быть менее точным.
- `InnerTubeClient` использует фиксированный WEB_REMIX context без входа в аккаунт
  пользователя; при сбое direct search/next сохраняется общий cooldown 15 минут.
  Relay возвращает каталог, не извлечённый аудиофайл; continuation direct-радио при
  переходе на relay не сохраняется как эквивалентная серверная сессия.
- Hitmos зависит от HTML/JSON-разметки и редиректов; каталожные запросы Deezer и
  InnerTube/relay имеют фиксированные лимиты/таймауты. Ошибки часто превращаются
  в пустые результаты: нельзя по ним однозначно отличить отсутствие трека от блокировки.
- В рассмотренных запросах Deezer нет OAuth-потока, а в InnerTube нет пользовательской
  авторизации. Поддержка закрытого/платного каталога и права скачивания не следуют
  из наличия URL. Актуальные условия API, квоты, лицензии, региональные ограничения,
  авторизация и разрешённость полного аудио требуют отдельной проверки перед подключением
  нового провайдера; здесь юридическая/сетевая проверка не проводилась.
- Без сети и устройства не установлены доступность доменов, пригодность MP3/CDN-ссылок,
  работа через VPN/SOCKS, полнота композиций и поведение при блокировке во время проигрывания.
  Цепочка Telegram-поиска и полный набор локальных импортов намеренно не исследовались.

## Одно минимальное направление расширения — резерв до передачи плееру

Добавить небольшой слой выбора поставщика **в существующий механизм поиска/разрешения URL**,
сохранив нынешний Hitmos первым источником и прежний контракт `MessageObject`/`SG_STREAM`.
Не строить новый музыкальный движок и не заменять алгоритм рекомендаций.
Это предложение, реализации в этой задаче нет.

1. Разделить результат каталога, результат разрешения аудио и скачивание. Минимально
   результат аудио должен различать полный трек, preview и отсутствие разрешённого URL,
   хранить идентификатор провайдера и сведения, нужные для запроса. Одного `downloadUrl`
   недостаточно для выбора между preview и полной записью.
2. В `MusicWebSearcher` свести разрешение аудио к одной точке: текущий Hitmos → один
   дополнительный независимо проверенный поставщик при ошибке/пустом результате.
   Поиск метаданных может сохранять Deezer. Не выдавать Deezer preview за полный fallback.
   Конкретный новый сервис сейчас не выбран: сначала подтвердить API, права, авторизацию,
   доступность из сети владельца и совместимость URL/формата с существующим плеером.
3. В `MusicNetworkHelper` явно согласовать маршруты «обычная сеть / настроенный SOCKS»
   для нового слоя, без скрытого переключения или запуска VPN/WS. Существующий системный
   VPN остаётся внешним условием. Не распространять смену глобального ProxySelector
   на весь клиент без отдельной необходимости.
4. Подключить общий resolver в `ChannelMusicFragment` и
   `wave/WaveQueueManager::resolveSingleCandidate`: сначала разрешить кандидата,
   затем вызвать прежний `createWebMessageObject`. `SmartRadioEngine`, InnerTube,
   очередь и `MusicPlayerService` оставить с прежними обязанностями.
   Загрузчик получает уже выбранное аудио; новый источник не должен требовать нового движка.

Риски: неверное совпадение треков разных каталогов, preview вместо полной записи,
истекающий URL/обязательные headers, неподдерживаемый формат, дополнительные задержки
и запросы, смена URL/hash ID и повторное создание записей в плейлистах/кэше.
Поэтому нужен ограниченный timeout и различение «не найдено / сеть / доступ запрещён»;
fallback не должен молча менять уже сохранённые треки или структуру очереди.
Первый этап покрывает резерв **до** запуска плеера. Восстановление после обрыва уже
играющего потока — отдельная задача, её нельзя обещать без вмешательства в воспроизведение.
Предварительная проверка ссылки тоже не гарантирует, что она не истечёт позднее.

Для последующей реализации достаточно затронуть `MusicWebSearcher.java`,
`MusicNetworkHelper.java`, выбранные вызовы `ChannelMusicFragment.java` и
`wave/WaveQueueManager.java` плюс небольшой адаптер нового поставщика при необходимости.
Формат существующих плейлистов и сохранённых `SG_STREAM` оставить читаемым;
совместимость старых записей, Волны, локального файла и фонового проигрывания
потребует отдельных сценариев приёмки после облачной сборки. Сейчас изменений кода нет.


## M1 / M2: уточнение после реализации Audius

Ветка `feature/music-sources`, M1 — `c805708fb`: добавлены `AudiusClient`,
`MusicSourceResolver`, независимая выдача Audius и точный резерв после Hitmos, включая Волну.
Audius в M1 используется только для открытого полного streaming, без офлайн-сохранения.
По сообщению владельца, на Pixel 8 подтверждены доступность API Audius и воспроизведение
в браузере; воспроизведение внутри Velora пока не подтверждено.

### M2 — YouTube Music: интеграция полного аудио остановлена

Точечно проверены исходники без клонирования репозиториев; внешние фрагменты не переносились:

| Репозиторий / проверенный commit | Роль и лицензия |
| --- | --- |
| [Metrolist `bc6c185094e921e54c21e970fa01b964e3c1eb0b`](https://github.com/MetrolistGroup/Metrolist/tree/bc6c185094e921e54c21e970fa01b964e3c1eb0b) | `DefaultStreamResolver`, `PlaybackResource`, Android token provider; GPL-3.0 |
| [innertubex `e4fb0003ce092beb71f3de464c661bf9f3f54c7f`](https://github.com/MetrolistGroup/innertubex/tree/e4fb0003ce092beb71f3de464c661bf9f3f54c7f) | `InnerTube`, `InnerTubeExtractor`, `PlayerResponse`; GPL-3.0 |
| [quackjs `d867d98f9f2562009399cdfecd67e626a086f878`](https://github.com/MetrolistGroup/quackjs/tree/d867d98f9f2562009399cdfecd67e626a086f878) | Преобразования player signature и `n`; README указывает GPL-3.0-only и сохранение third-party notices |

Механизм: поиск/метаданные InnerTube → запрос `player` с клиентским контекстом →
выбор аудиоформата и транспорта → при необходимости обработка cipher/`n` через QuackJS →
ресурс с URL, HTTP-заголовками, сроком действия и, для SABR, дополнительным bootstrap.
Поиск не требует извлечения аудио. Авторизация для некоторых открытых сценариев необязательна;
cookies/SAPISIDHASH и PO-токены зависят от клиента и режима доступа. Android token provider
использует WebView-возможности и локальный bound service: слово `Remote` в имени minter
не означает обязательный новый сервер. Remote player config/Faraday hints опциональны;
встраивание всего механизма всё равно существенно больше небольшого REST-адаптера.
См. [описание extraction](https://github.com/MetrolistGroup/innertubex/blob/e4fb0003ce092beb71f3de464c661bf9f3f54c7f/README.md).

Ссылки временные: `InnerTubeExtractor::streamExpiry` учитывает `expire` и `expiresInSeconds`,
берёт ближайший срок; универсальный срок «N часов» не установлен. Обычный совместимый
HTTP-аудиопоток потенциально подходит плееру Velora, но одного сохранённого URL недостаточно
для обновления срока/специальных headers. SABR — не обычная ссылка на аудиофайл:
нужен отдельный транспорт; текущий контракт `SG_STREAM` его не предоставляет.
Региональный доступ и пригодность конкретных потоков не подтверждены сетевыми тестами.

В Velora уже есть `InnerTubeClient.searchSongs/fetchRadioBatch/fetchPlaylist` и Piped-reserve
каталога. Нет `player`, извлечения YouTube-аудио, signature/`n` обработки или SABR-транспорта.
Волна получает полный аудио-URL через Hitmos, затем точный Audius-reserve M1;
добавление ещё одного каталожного запроса само по себе не расширит воспроизводимый каталог.

**Причина остановки:** не обоснован разрешённый способ передавать извлечённое YouTube-аудио
в сторонний фоновый `MediaController`. [YouTube Terms, Permissions and Restrictions](https://www.youtube.com/static?template=terms)
ограничивают неразрешённое извлечение/использование контента и автоматизированный доступ;
[Developer Policies III.D.7, III.E.1, III.I](https://developers.google.com/youtube/terms/developer-policies)
дополнительно ограничивают скачивание без согласования, отделение аудио, фоновый плеер,
обход географических ограничений и получение audiovisual content вне API Services.
Это основание остановиться по условиям M2, а не заключение о законности всех сторонних клиентов.
Подпись/`n` не следует автоматически называть DRM, но наличие открытого кода или Premium
не подтверждает разрешение на такой перенос. Лицензии кода также не предоставляют права
на контент/сервис; перед копированием требовалась бы отдельная проверка совместимости
GPL-3.0 с условиями всех затронутых компонентов Velora и сохранение notices/авторства.

Следующий кандидат для отдельной задачи — [Jamendo tracks API](https://developer.jamendo.com/v3.0/tracks):
есть поиск, `audio` для streaming, отдельно `audiodownload` и `audiodownload_allowed`.
Нужен зарегистрированный `client_id`, принятие API Terms и проверка лицензий/атрибуции;
это рекомендация исследовать официальный источник, не подтверждение готовой интеграции.
В M2 исходники/зависимости/маршрутизация не изменены. Повторно прошли 73 host-проверки M1
и синтаксический разбор изменённых в M1 Java-файлов; Android-сборки и YouTube-аудиотесты не запускались.


### M2 — продолжение: direct AAC без переноса extractor

Предыдущий раздел сохранён как результат первого прохода. В продолжении реализован
ограниченный технический путь; юридический этап повторно не проводился.
В существующий `wave/InnerTubeClient` добавлены ограниченные `search`/`player`-запросы.
Из изученного InnerTubeX использованы сведения о профиле `ANDROID_VR_NO_AUTH` и контракте
«URL + headers + expiresAt». Реализации Metrolist/InnerTubeX/QuackJS не копировались,
библиотеки, cipher solver, токен-сервисы и новые зависимости приложения не добавлены;
проверенные версии и лицензии источников указаны выше.

`YouTubeMusicClient` принимает только ответ `OK` для нужного video ID, конечную запись
и прямой HTTPS audio-only AAC-LC (`audio/mp4`, `mp4a.40.2`) на `*.googlevideo.com`.
Длительность формата сопоставляется с полной длительностью; video/muxed, preview,
DRM, cipher/signatureCipher, URL с `n`/`s`/`pot`, live и SABR-only пропускаются.
Не выполняются вход, получение PO-токенов, расшифровка или обход ограничений доступа.
Это существенно меньший поддерживаемый набор, чем полный extractor Metrolist.

Новая композиция хранит стабильный `https://music.youtube.com/watch?v=<videoId>` в прежнем
`SG_STREAM`, а не временный CDN URL. `YouTubeMusicDataSource` использует уже имеющийся
Media3 `ResolvingDataSource`: непосредственно перед HTTP-open подставляет URL и заголовки,
сохраняя position/length/key и сообщая наружу стабильный URI. Потоки не сохраняются на диск.
Кэш до 32 ресурсов — только в памяти; срок берётся по минимуму `expire` и `expiresInSeconds`,
с запасом 30 секунд. Истёкшая ссылка запрашивается заново при новом соединении/seek;
если обновление не удалось, старая ссылка не возвращается. Смена itag/размера файла при
повторном открытии отклоняется, чтобы не применить старые byte offsets к другому формату.
Досрочный отзыв ещё действующей
ссылки не имеет отдельного механизма восстановления; ошибку обрабатывает существующий плеер.

В поиске YouTube добавляется независимо от завершения Hitmos/Audius, только на первой странице;
проверяется до трёх кандидатов, поздние результаты проходят имеющуюся защиту актуальности запроса.
Для сопоставления по названию порядок — Hitmos → Audius → точное соответствие YouTube.
В Волне известный video ID сначала проверяется непосредственно в YouTube, затем сохраняется
прежний путь Hitmos/Audius. Алгоритмы рекомендаций, история и структура очереди не изменены.
Файловые действия получили тот же stream-only guard, который уже был для Audius;
старые записи, локальные файлы и Telegram-аудио не мигрируются.

Проверки: 73 host-проверки M1 и 99 проверок M2; компиляция адаптера/сетевых классов на JVM,
реальный Media3 `ResolvingDataSource` с тестовыми HTTP/Android API и извлечённый production-метод
создания `MessageObject`; синтаксический разбор Android-точек интеграции. Android-сборка не запускалась.
Пробный запрос только player-метаданных из среды Codex завершился таймаутом TLS;
реальная доступность AAC и воспроизведение YouTube в Velora не подтверждены.
На Pixel 8 нужны поиск, переход между треками/источниками, фон, seek после истечения URL,
Волна, отказы сети и прежние Hitmos/Audius/Telegram/локальные треки.

### M3 — JioSaavn: остановка на проверке доступности полного аудио

Точечно проверен [sumitkolhe/jiosaavn-api, commit fc6bd132193d1fc71c2ab3db373e78b92884f67c](https://github.com/sumitkolhe/jiosaavn-api/tree/fc6bd132193d1fc71c2ab3db373e78b92884f67c),
MIT, Copyright (c) 2024 Sumit Kolhe. Код не переносился, репозиторий не клонировался.
`fetch.helper.ts` обращается непосредственно к `https://www.jiosaavn.com/api.php`:
`search.getResults` с q/p/n и `song.getDetails` с pids, `_format=json`, `_marker=0`,
`api_version=4`, `ctx=web6dot0`. Свой сервер для этих запросов технически не требуется.
Это внутренний endpoint, описанный исходниками wrapper, а не найденный официальный
документированный API выдачи общедоступного полного аудио; документация wrapper — отдельный сервис.
Ответы содержат стабильный song ID, title, duration, image и `artistMap`.

[link.helper.ts](https://github.com/sumitkolhe/jiosaavn-api/blob/fc6bd132193d1fc71c2ab3db373e78b92884f67c/src/common/helpers/link.helper.ts)
декодирует Base64/DES-ECB поле `encrypted_media_url` и заменой `_96` формирует варианты
12/48/96/160/320 kbps. Это обработка адреса, не расшифровка аудиоконтента.
[song.helper.ts](https://github.com/sumitkolhe/jiosaavn-api/blob/fc6bd132193d1fc71c2ab3db373e78b92884f67c/src/modules/songs/helpers/song.helper.ts)
вызывает её без проверки `more_info.rights`; наличие `downloadUrl` у wrapper поэтому
не подтверждает ни свободный полный доступ, ни разрешение всех сгенерированных качеств.

**Конкретный результат живых запросов из среды Codex:** без cookies/авторизации API
вернул HTTP 200 для четырёх поисков: electronic (1 запись), Arijit Singh, Happy Birthday,
Creative Commons (по 5). У всех 16 записей `rights.code="1"`, `reason="Pro Only"`,
хотя `encrypted_media_url` заполнено. Повторный `song.getDetails` для SWZKcjcD также
вернул Pro Only. [JioSaavn Music Rights](https://corporate.saavn.com/music-rights)
поясняет, что Pro Only означает доступ для платных подписчиков; доступность зависит
в том числе от региона/платформы. `cacheable=true` не отменяет этот статус.

В рамках этих проверок не получен ни один подтверждённый свободный полный трек.
Аудиоссылки ограниченных записей не декодировались, аудио не загружалось, регион,
прокси и авторизация не подменялись. Срок жизни ссылок, необходимые media headers,
реальный формат и пригодность для MediaController поэтому не подтверждены.
Это ограниченная выборка из конкретной сети, а не вывод о всём каталоге во всех регионах.
Для продолжения нужен проверяемый доступный без Pro трек и ответ прав доступа из сети
Pixel 8 либо отдельный разрешённый механизм авторизованного доступа.

M3 остановлен: адаптер без проверки прав игнорировал бы платный доступ, а адаптер,
отбрасывающий все фактически проверенные записи, сейчас не даёт подтверждённого расширения
воспроизводимого каталога. Исходники M1/M2 не изменены; новые форматы и тесты не добавлены.
Проверены живые ответы поиска/деталей и `git diff --check`; прежние JVM-тесты не
перезапускались, поскольку код не менялся. Пустой коммит M3 не создавался.
